### 3.4 State machines

#### Task

Allowed states:

- `Draft`
- `Ready`
- `In progress`
- `In review`
- `Done`
- `Blocked`
- `Cancelled`

Core progression:

`Draft → Ready → In progress → In review → Done`

Blocked can be entered from active states and returned to `Ready` or `In progress`. `In review` can return to `In progress` when revision is requested. Any active state may transition to `Cancelled`, with a reason attached.

#### Run

Allowed states:

- `queued`
- `running`
- `quota-held`
- `disconnected/uncertain`
- `failed`
- `cancelled`
- `completed`

Heartbeat loss means `disconnected/uncertain`, not proven success or failure. Cancellation remains requested until acknowledged; the system must not silently claim process termination.

#### Assignment lease

Assignment is a renewable lease:

- `available` → `claimed`
- `claimed` → `active`
- `active` may be renewed by heartbeat
- Expiry triggers `reconciling`
- Reassignment happens only after reconciliation prevents stale overwrite

Multiple competing candidates are supported. A task may have competing candidate assignments, but only one active assignment wins the unit.

## 4. Run-policy mapping

### 4.1 Council stages

At each council stage — planning and final review — the DSH connector must:

1. Open the live Council Budget panel.
2. Capture the exact selected seat set.
3. Identify every seat by model.
4. Report any unavailable seat.
5. Stop before spend if any seat is unavailable.

No alternative model may be selected. No seat may be added, substituted, or omitted because a seat is unreachable.

The stage gate UI must display the seat roster and each seat’s availability before the user approves the stage.

### 4.2 Swarm economy mode

The build stage must run exactly under DSH economy mode as defined in the current implementation. Economy mode is token-efficient and reduces resource consumption [9]. The dsh-swarm pipeline includes the six roles: orchestrator, planner, reviewer, wiki bridge, executor, and implementation reviewer [7].

For this project:

- Free seats contest every unit.
- Exactly one winner is selected per unit.
- Paid seats review and perform bounded fallback.
- Fallback is bounded by an explicit cap on tokens, cost, or attempts.
- If the fallback cap is exceeded, the unit must go to `quota-held` or `failed`, not continue spending without limit.
- Per-candidate artifacts and review attribution must be retained.
- The platform must not duplicate DSH orchestration.

### 4.3 Economy estimate at the swarm gate

The swarm gate must show an economy estimate before execution is authorized. The estimate must use the current DSH pricebook snapshot [6] and account for:

- DSH harness cost: zero [5]
- Session and subagent cost totals [6]
- Exact selected seat models from the Council Budget panel
- Number of planned units
- Estimated prompt/completion tokens
- Free contestant cost, where applicable
- Paid review cost
- Bounded fallback cost
- Concurrency limits
- Spending/time limits

The estimate must show:

- Pricebook snapshot ID
- Snapshot effective timestamp
- Per-unit breakdown
- Total estimated cost
- Expiry
- Explicit `unknown` for unavailable usage/cost

Unknown usage is not zero. The estimate is a gate input, not an entitlement to exceed the approved limit.
